VISUAL COMPONENT COVERAGE — TODO
=================================
Tracks which math levels have an authored visual practice component (per
MATH_TSX_STYLE_GUIDE.txt conventions) and which still need one. Word
problems don't need this list — the generation pipeline is level-agnostic
and works for any level already (see Student Portal plan, Phase 3/4).

Status legend: [x] authored AND wired into LEVEL_SKILLS (live for students)
               [~] authored but NOT wired in yet (invisible to students —
                   this is the state that caused a live "no practice
                   problems" bug for MG6 on 2026-09-02, so don't assume
                   a component existing means it's actually reachable)
               [ ] needs one authored

When a level gets a new component:
  1. Write it per MATH_TSX_STYLE_GUIDE.txt (named export + Demo default export),
     inside that level's own folder: src/pages/math-levels/{levelId}/{fileName}.tsx.
  2. Add an entry to LEVEL_SKILLS in src/utils/levelSubsections.ts (type,
     skillId, componentFile, componentExport, generateParams) — do this
     immediately, don't leave it for later. A component isn't "done" until
     this step happens; that's the step that actually makes it show up in
     a student's Practice Problems card.
  3. Check this file's box and note the component name below.

[x] MK1  — CountingAndCardinalityLab    (MK1/MK1_CountingAndCardinalityLab.tsx) —
          wired as a "standalone" skill, the first Kindergarten lab and the first
          lab anywhere in the K-8 curriculum built on top of concrete, countable
          objects rather than bare numerals from the start. Covers all of K.CC
          (K.CC.1-7) in one module: Counting On and Counting Forward (K.CC.1-2),
          Writing and Matching Numerals (K.CC.3), How Many? / Cardinality and
          Counting Objects (K.CC.4a-c, K.CC.5 — folds K.CC.4c's "one more" check
          into THIS unit's CFU rather than Unit 1's, since it's as much about
          cardinality as sequencing), and Comparing Groups and Numerals (K.CC.6-7)
          — four units, each with a required Explore/Check-for-Understanding/
          Practice/Test tab, plus a cumulative 20-question Module Test (5 per
          unit, passScore 16). Entry file + styles
          (MK1_CountingAndCardinalityLab_styles.css, scoped under .cc-lab) are
          flat in MK1/ (admin file browser glob, same reasoning as every other
          multi-file Lab); supporting diagrams/ and units/ live one level
          deeper, inside MK1/CountingAndCardinalityLab/.

          Two new shared-shape (but lab-local, not promoted — this is their
          first consumer) diagrams, since no existing diagram in shared/diagrams/
          shows a literal countable group of objects: CounterGroup.tsx (dots or
          an emoji glyph laid out as a line/grid/circle/random scatter, with an
          optional click-to-count interactive mode for Explore — see the style
          guide note added alongside this entry) and TenGroups.tsx (any count
          0-100 shown as bundled 2x5 "ten frame" blocks plus loose ones, so
          counting by tens and numbers above 20 still have something concrete
          backing them). A third small local component, MatchingRows (duplicated
          between ComparingGroupsAndNumerals.tsx and its Test file, same
          intentional duplication convention as every *Test.tsx in this app),
          renders two fixed-gap left-aligned rows so one-to-one matching pairs
          visibly line up, with the unmatched "extra" counters past the shorter
          row's length drawn dashed — the literal visual tell for "this row ran
          out first."

          No new shared/engine Step kinds were needed — every question uses the
          existing "number" and "choice" kinds. The one new technique (not a new
          Step kind) is embedding two renderings of the same glyph in a
          ChoiceStep's prompt — one plain, one CSS-mirrored (`scaleX(-1)`) — with
          the choices being positional labels ("Left"/"Right") rather than the
          glyph text itself, for Writing and Matching Numerals' reversed-numeral
          recognition bucket.

          Every unit's Check-for-Understanding is 4 fixed (non-randomized)
          questions, each targeting a specific, named misconception per the
          plan: Unit 1 drills the decade-transition garble ("...29, twenty-
          ten..."); Unit 2 drills visually-similar-numeral confusion (6/9, 2/5,
          1/7) including a false-generalization trap (NOT every look-alike pair
          is actually a mirror-flip — 6/9 are, 2/5 and 1/7 aren't); Unit 3
          drills the core cardinality misconception (the LAST number counted is
          the TOTAL, not a label on the last object touched) plus K.CC.4c's
          "one more"; Unit 4 drills the "takes up more space = more objects"
          misconception directly, per the plan's explicit requirement.

          Autonomous decisions beyond the approved plan (all documented in the
          build's final report): the plan's 3rd Unit-4 bucket ("close vs.
          obvious difference") was built as ONE bucket with two randomized
          difficulty regimes (both independently guaranteed reachable by the
          verification script) rather than two separate buckets, matching how
          the plan phrased it ("close comparisons are the harder bucket" within
          one described skill, not two). "Spoken/heard" numbers (K.CC.3) are
          simulated as the spelled-out number word, since this app has no audio
          engine. countOut's (K.CC.5 reverse-direction) "take" range was widened
          in the Test file's dedicated nearExhaustion variant to guarantee the
          near-total-depletion edge (1-2 left) is actually tested, not just
          reachable by chance in Practice.

          UnitView's introSatisfied short-circuits to always-true regardless of
          reintroEverySolved, so setting it would be silently inert dead code, not
          actual periodic re-gating. Built as requiresIntro: false with
          reintroEverySolved omitted (matching the plan's primary intent — pure
          fluency practice on already-gated concepts, no new gate) rather than setting
          a field that does nothing; enabling real periodic re-checking without an
          initial gate would need an engine change to UnitView's gating logic itself,
          out of scope for this lab's own folder.
