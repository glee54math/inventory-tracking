MATH LEVEL TSX STYLE GUIDE
==========================
Derived from analysis of every implemented file in src/pages/math-levels/:
MG1 (TenFrame), MG2 (PartPartWhole), MG3 (MakeTenStrategy), MG5 (TapeDiagram),
MG6 (NumberLine), MG6_TwoDigitVisualAddition, MG6_VerticalAddition (VerticalMath),
MG7_Nx1DigitMultiplication (Nx1Multiplication), Nx1VertMult, WordProblems +
WordProblemData.

Purpose: this is the spec to hand Claude (or a human) when authoring a NEW
visual practice component for the Student Portal. Follow it exactly so
generated files are drop-in compatible with the existing level pages and
with the future ProblemRenderer / problemBank pipeline. Most level shell
files (MG4, MG7-11, MH1-6, MK1-4, MM1-3, and every EG/EH/EK/EM file) are
still empty — this guide is what fills them.

------------------------------------------------------------------
1. FILE ANATOMY
------------------------------------------------------------------
Every implemented file follows this exact section order, marked with
banner comments:

    import React, { useState } from 'react';   // + useRef, useMemo, useEffect as needed

    // ============================================================================
    // TYPE DEFINITIONS
    // ============================================================================
    export interface XxxProps { ... }

    // ============================================================================
    // UTILITY FUNCTIONS
    // ============================================================================
    const getSizeClasses = (size) => ({ ... }[size]);
    // + any pure math/decomposition helpers

    // ============================================================================
    // PRIMITIVE COMPONENTS   (only if the model needs reusable sub-pieces)
    // ============================================================================
    const CircleNode: React.FC<...> = ...
    const MathInput: React.FC<...> = ...

    // ============================================================================
    // MAIN COMPONENT
    // ============================================================================
    export const Xxx: React.FC<XxxProps> = ({ ...props }) => { ... };

    // ============================================================================
    // DEMO COMPONENT
    // ============================================================================
    const XxxDemo: React.FC = () => { /* page shell + 2-3 worked examples */ };
    export default XxxDemo;

Naming rule: the MAIN COMPONENT is a NAMED export (`export const Xxx`).
The DEFAULT export is always the Demo wrapper, never the reusable
component itself. Anything that imports the skill for real use (a level
page, or the future ProblemRenderer) imports the NAMED export, e.g.:
    import { Nx1Multiplication } from './MG7_Nx1DigitMultiplication';

Folder structure: every level has its own folder at
src/pages/math-levels/{levelId}/ (e.g. src/pages/math-levels/MG7/). A file
inside that folder matching the folder name exactly (e.g. MG7/MG7.tsx) is
a ROUTED LEVEL SHELL — LevelsPage.tsx dynamically imports it by URL param
(math-levels/{levelId}/{levelId}.tsx). A file named `{levelId}_{SkillName}.tsx`
(e.g. MG7/MG7_Nx1DigitMultiplication.tsx) is a SKILL COMPONENT living
inside that same level folder — a building block, not directly routed.
New AI-generated problem components should use the skill-component naming
pattern and live inside their level's folder; nothing should be written
directly into the empty `{levelId}/{levelId}.tsx` shells as part of this
pipeline. Files that aren't tied to one specific level (WordProblems.tsx,
WordProblemData.ts, WordProblemsPrintable2x2.tsx) stay at the top of
src/pages/math-levels/, not inside any level folder.

------------------------------------------------------------------
2. THE STANDARD PROP CONTRACT
------------------------------------------------------------------
Every main component accepts (a subset of) these, always optional except
the problem-defining numeric props:

    showFeedback?: boolean       // reveal green/red correctness styling
    showWork?: boolean           // reveal scratch-work annotations (carries/
                                  // borrows) — SEPARATE from showFeedback
    size?: 'sm' | 'md' | 'lg'    // default 'md', drives a size->classes map

The problem itself is always passed as plain numeric/string props (num1,
num2, addend1, addend2, parts, nums, whole, part1, part2, operation, ...).
The correct answer is NEVER passed in as a separate prop — it is always
derived from the numeric props via a pure function. This matters for the
problem bank: caching a component instance only requires storing its
input props; the answer key is reproducible from those props alone. The
one exception is WordProblem, which resolves randomness (person/unit/
template) once via useMemo on mount — see section 6.

------------------------------------------------------------------
3. STATE, INPUT, AND VALIDATION PATTERN
------------------------------------------------------------------
- Every fillable blank is a `useState<string>` (never number — inputs are
  strings so an empty box can exist). For grids (vertical math), a single
  `useState<{[key: string]: string}>` keyed by `"row-col"` is used instead
  of one useState per cell.
- Input onChange always regex-guards to digits only, e.g.:
      onChange={(e) => {
        const v = e.target.value;
        if (v === '' || /^\d+$/.test(v)) onChange(v);
      }}
  Single-digit grid cells use `/^\d$/` with `maxLength={1}`.
- Correctness check is always a tiny inline helper, e.g.:
      const isCorrect = parseInt(value) === correctAnswer;
  Feedback only renders `if (showFeedback && value)` — never shows red on
  an empty box.
- Feedback color convention (use exactly these Tailwind classes):
      correct:   border-green-500 bg-green-50 (or bg-green-100) text-green-800
      incorrect: border-red-500 bg-red-50 text-red-800
      neutral:   border-gray-800 bg-white
  Use the `!` important-prefix (e.g. `!bg-green-50`) only when overriding
  another background utility already on the element (matches existing
  usage in VerticalMath / Nx1VertMult).
- Focus ring: `focus:outline-none focus:ring-2 focus:ring-blue-400
  transition-colors` on every input.

------------------------------------------------------------------
4. SIZE VARIANTS
------------------------------------------------------------------
Always define a local `getSizeClasses` / `getSizeConfig` function mapping
`'sm' | 'md' | 'lg'` to a small object of Tailwind width/height/text
classes (see MG1/MG2/MG3/MG5 for the circle-based table, and
VerticalMath/Nx1VertMult for the identical digit/box/carry table used by
every vertical-format component — reuse that exact table for any new
vertical addition/subtraction/multiplication/division component so they
stack visually).

------------------------------------------------------------------
5. LAYOUT RULES
------------------------------------------------------------------
- The MAIN COMPONENT renders bare: `flex flex-col items-center gap-N p-N`
  (or `items-end` for right-aligned vertical math). It must NEVER include
  page chrome (`min-h-screen`, gradient backgrounds, `max-w-*-mx-auto`
  wrappers, `<h1>` titles). That chrome belongs only in the Demo wrapper.
  This is required so the component can be embedded directly into the
  future practice-session page without fighting its own page shell.
- Multi-step problems (Nx1Multiplication) use a numbered "STEP 1 / STEP 2
  / STEP 3" pill pattern:
      <span className="bg-indigo-500 text-white text-xs font-bold px-3
        py-1 rounded-full tracking-wide">STEP 1</span>
  with a following instruction sentence, then the step's interactive
  region.
- Connecting-line diagrams (PartPartWhole, MakeTenStrategy,
  TwoDigitVisualAddition) share one technique: a `containerRef` plus one
  `useRef` per node, an absolutely-positioned `<svg>` overlay sibling,
  and a `useEffect` that measures `getBoundingClientRect()` on each ref
  relative to the container and sets `<line>` coordinates. Recompute on
  `[size, ...relevant state]`. Reuse this technique for any new
  decomposition/bar-model visual rather than inventing a new one.
- Vertical-format problems (VerticalMath, Nx1VertMult) share one
  skeleton: `flex flex-col items-end`, an optional carry/borrow row above
  the operands, right-padded operand rows, a horizontal rule sized to
  `maxDigits * cellPx`, and a result row of single-digit inputs. They
  also share identical keyboard navigation: a sorted `inputRefs` dict
  keyed `"row-col"`, Tab/Shift+Tab and ArrowLeft/ArrowRight move through
  cells in key order, ArrowUp/ArrowDown move by row.
- Place-value color coding (Nx1Multiplication's area model): a fixed
  array indexed by place (0=ones orange, 1=tens green, 2=hundreds sky,
  3=thousands violet), each entry giving border/bg/headerBg/text/label/
  inputBorder/ring classes. Reuse this exact palette for any new
  place-value decomposition component so color meaning stays consistent
  across levels.

------------------------------------------------------------------
6. WORD PROBLEMS ARE TEMPLATE-GENERATED, NOT FREE TEXT
------------------------------------------------------------------
WordProblemData.ts holds the randomizable content pools: PEOPLE (name +
pronoun + possessive), UNITS (singular/plural + category: food/object/
money/abstract, used to pick a matching verb), keyword banks per
operation/context, and SentenceTemplate objects with `{name}` `{num1}`
`{unit1}` `{verb}` `{keyword}` etc. placeholders.

WordProblems.tsx (WordProblem component) picks a random person/unit/
template ONCE via `useMemo(() => ..., [])` (empty deps — must not
re-roll on re-render), fills the template with string `.replace()`,
computes the numeric answer arithmetically from the `nums`/`operation`
props, and also builds a `segments: {text, label?}[]` array so the
"help" mode can underline and label the name/units/keyword inline.
Grading compares typed answers (name, result number, units, keyword)
case-insensitively, and is commutative-aware for add/mult (order of
typed numbers doesn't matter) but order-sensitive for sub/div.

Any new word-problem generator (including future Claude-authored ones)
should follow this same shape: `{ text, keyword, segments }` output plus
a numeric `answer`, so it can plug into the existing `WordProblem`
rendering component instead of inventing new markup.

------------------------------------------------------------------
7. KNOWN DUPLICATION — DO NOT "FIX" IT DURING GENERATION
------------------------------------------------------------------
`CircleNode` and `MathInput` are re-defined nearly verbatim inside MG2,
MG3, and MG6_TwoDigitVisualAddition (not imported from a shared module).
This is the established convention in this codebase — each skill file is
self-contained and copy-pastes its primitives rather than importing a
shared library. New generated files should do the same (copy the
primitive definitions in, don't invent an import from a nonexistent
shared components file) unless a future refactor explicitly introduces a
shared primitives module.

------------------------------------------------------------------
8. DEMO / DEFAULT EXPORT CONVENTION
------------------------------------------------------------------
Every file ends with a default-exported `XxxDemo` component: page-chrome
wrapper (`min-h-screen bg-gradient-to-br from-blue-50 to-purple-50 p-8`,
`max-w-*xl mx-auto`), an `<h1>` + subtitle, 2-3 example cards each with
its own `showFeedback`/`showWork` `useState` toggle and a "Check Answer"
/ "Show Work" button (`!bg-green-500` / `!bg-blue-500`, white text,
rounded-lg), and a closing "Component Features" bullet list. This exists
for standalone preview/QA of the component in isolation — keep writing it
for every new skill file (useful when eyeballing a newly generated
component), but note the Student Portal will never render this default
export; it always imports the named component directly.

------------------------------------------------------------------
9. MINIMAL TEMPLATE FOR A NEW SKILL COMPONENT
------------------------------------------------------------------
    import React, { useState } from 'react';

    // ============================================================================
    // TYPE DEFINITIONS
    // ============================================================================
    export interface {Skill}Props {
      // problem-defining numeric/string props (e.g. num1, num2)
      showFeedback?: boolean;
      size?: 'sm' | 'md' | 'lg';
    }

    // ============================================================================
    // UTILITY FUNCTIONS
    // ============================================================================
    const getSizeClasses = (size: 'sm' | 'md' | 'lg' = 'md') => ({
      sm: { /* ... */ },
      md: { /* ... */ },
      lg: { /* ... */ },
    }[size]);

    // ============================================================================
    // MAIN COMPONENT
    // ============================================================================
    export const {Skill}: React.FC<{Skill}Props> = ({
      showFeedback = false,
      size = 'md',
      // ...problem props
    }) => {
      // derive correct answer(s) from props here — pure functions only
      // one useState per fillable blank, regex-guarded to digits
      return (
        <div className="flex flex-col items-center gap-6 p-6">
          {/* bare component markup, no page chrome */}
        </div>
      );
    };

    // ============================================================================
    // DEMO COMPONENT
    // ============================================================================
    const {Skill}Demo: React.FC = () => {
      const [showFeedback1, setShowFeedback1] = useState(false);
      return (
        <div className="min-h-screen bg-gradient-to-br from-blue-50 to-purple-50 p-8">
          <div className="max-w-3xl mx-auto">
            <h1 className="text-4xl font-bold text-gray-800 mb-2">{Skill Title}</h1>
            <p className="text-gray-600 mb-8">{one-line description}</p>
            <div className="bg-white rounded-lg shadow-md p-6 mb-6">
              <div className="flex justify-center mb-2">
                <button
                  onClick={() => setShowFeedback1(!showFeedback1)}
                  className="px-6 py-2 !bg-green-500 text-white rounded-lg font-medium hover:!bg-green-600 transition-colors"
                >
                  {showFeedback1 ? 'Hide' : 'Check'} Answer
                </button>
              </div>
              <{Skill} /* ...example props */ showFeedback={showFeedback1} size="md" />
            </div>
          </div>
        </div>
      );
    };

    export default {Skill}Demo;

10. WHAT'S STILL UNDOCUMENTED (fill in later, per level)
------------------------------------------------------------------
This guide covers HOW to write a component. It does not yet cover WHICH
skill belongs on which pages within a level's 110-page range (that's the
"page subsection" documentation mentioned in the Student Portal plan —
tracked separately in src/utils/levelSubsections.ts as it's authored).

NOTE (added with MK1_CountingAndCardinalityLab, 2026-10): sections 1-11
above describe the ORIGINAL Tailwind-props-based pipeline (TenFrame,
VerticalMath, Nx1Multiplication, etc.) — generateParams()/showFeedback,
one bare component per skill. Every "Lab" built since MM1_RatioLab (MM1,
MG9, MG11, and now MK1) instead uses a completely different, newer
architecture: shared/engine's Unit/Problem/Step/TestQuestion contracts,
StepProblem.tsx/UnitTest.tsx for grading and test-taking chrome, and
shared/diagrams for visuals — wired in as a "standalone" skill, not a
"visual" one. This guide does not cover that architecture at all; the
living reference for its conventions is VISUAL_COMPONENT_TODO.txt's
per-lab entries below, not this file. Any new K-8 "Lab" should follow
that newer pattern (read an existing Lab's own units/ folder first), not
sections 1-11's template.

Two reusable techniques introduced building MK1_CountingAndCardinalityLab,
worth reaching for again in any future Kindergarten/early-grade lab that
needs concrete, countable objects rather than bare numerals:
  - Click-to-count interaction (MK1/CountingAndCardinalityLab/diagrams/
    CounterGroup.tsx's `countedOrder`/`onToggle` props): each object can be
    clicked exactly once, in any order, with a small running badge showing
    its position in the student's own click order — deliberately NOT
    order-sensitive for the total (clicking in a different order still
    gives the same count), since that's itself the point being taught.
    Only meaningful in an Explore sandbox; Practice/Test visuals stay
    static.
  - Orientation-based recognition questions (used by Writing and Matching
    Numerals' "reversedPairs" bucket): when two choices differ only by a
    CSS transform (e.g. a mirrored `scaleX(-1)` numeral) rather than by
    different text, embed both renderings directly in the ChoiceStep's
    `prompt` (a ReactNode, so this needs no engine changes) and make the
    choices positional labels ("Left"/"Right") instead of the glyph itself
    — randomize which side is correct so the position itself can't be
    pattern-matched.

Two more reusable techniques introduced building
MK2_AdditionSubtractionAndTeenNumbersLab (the second Kindergarten lab),
worth reaching for again in any future K-1 lab that teaches part-part-whole
or place-value ideas:
  - A two-toned "split" diagram (MK2/AdditionSubtractionAndTeenNumbersLab/
    diagrams/SplitGroup.tsx): one group of objects where the first `partA`
    render in one tone and the rest in a second, with an optional dashed
    divider between them. This is the concrete stand-in for "put together"/
    "take apart"/decomposing a single whole into two colored parts — distinct
    from a single-tone counting diagram (MK1's CounterGroup, this lab's
    ObjectGroup) and from TWO separate single-tone diagrams side by side
    (used for comparing two SEPARATE quantities, not one whole split in two).
  - A single fixed-size ten-frame (MK2/.../diagrams/TenFrame.tsx), capped at
    exactly 10 cells and optionally two-toned (a `filled` count in one tone,
    plus a `fillB` complement count in a second tone filling the remaining
    cells) — the direct visual for "how many more to reach 10," distinct
    from MK1's TenGroups, which bundles an unbounded count (0-100) into
    REPEATING ten-blocks for counting-by-tens. Reach for TenFrame when the
    lesson is specifically about ONE frame's complement (Making 10, teen
    numbers as ten-plus-ones); reach for TenGroups-style repeating blocks
    only when the count can exceed 10 and the repetition itself is the point.
  NOTE: ObjectGroup.tsx above is a near-verbatim duplicate of MK1's
  CounterGroup.tsx, not a promotion to shared/diagrams/, because the build
  that introduced it was scoped to touch only its own lab's folder (plus
  this file, VISUAL_COMPONENT_TODO.txt, and levelSubsections.ts) — see
  VISUAL_COMPONENT_TODO.txt's MK2 entry for the full reasoning. This is the
  SECOND lab needing this exact shape, which is normally this codebase's own
  trigger to promote on the second real consumer rather than add a second
  silent copy — a future session with broader scope should do that
  promotion rather than letting a third lab duplicate it again.

Two durable conventions from MG10_AddingAndSubtractingFractionsLab (2026-11),
for any Unit-engine lab whose answers are fractions:
  - Type fractions and mixed numbers with the shared "fraction" Step kind
    (fractionStep() in shared/engine/types.ts: whole box + stacked boxes).
    Set `simplest: true` when simplest form is part of the skill: an equal
    but unsimplified answer is then rejected with a named message AND the
    solve stops counting as clean. Use one layout (whole box shown) for
    every final answer, so the layout never hints whether the answer is
    proper, mixed or whole.
  - The "Try one like it" retry lock is not K-1 only. Any lab can pass
    onRetrySame/onHelped to StepProblem and copy MK1's UnitView lock
    (owesRetry, drawRef, usedTokenRef, disabled type switch) without
    EarlyLearnerProvider; StepProblem words the wrap-up for the grade.
  - The retry DEBT lives in the lab component, not in UnitView
    (shared/engine/retryDebt.ts: useRetryDebts + bagItems/debtItem).
    UnitView is keyed by unit id, so a debt kept in its own state was
    cleared by switching units or reloading (MG10 review C1-01). The lab
    keeps one debt per unit, mirrored to sessionStorage
    (`retryDebt:{MODULE_ID}:{studentId}`); UnitView starts in the owed
    problem kind with the lock on. MK1-MK4, MG1 and MG10 do this.

11. MULTI-FILE SKILLS (exception to section 1's "one file" rule)
------------------------------------------------------------------
Most skills are one self-contained file. A skill can legitimately need
several (diagram + equation UI + feedback + shared logic + types) —
MG6_BarModel is the first example. When that happens:

  - All files stay FLAT as siblings directly inside the level folder — no
    subfolder. Prefix every supporting file with the main file's full
    name + underscore, e.g. MG6_BarModel.tsx is the entry point, and
    MG6_BarModel_Diagram.tsx, MG6_BarModel_EquationRow.tsx,
    MG6_BarModel_types.ts etc. are its supporting files. This keeps
    filenames self-documenting in LevelFilesPage's file list and avoids
    collisions with whatever the NEXT skill added to that same level
    folder happens to also need to call "types.ts" or "Feedback.tsx".
  - The entry file still needs a named export (not just default) if it's
    going into LEVEL_SKILLS — see levelSubsections.ts's componentExport.
  - If the component doesn't fit the generateParams()/showFeedback
    contract section 2 describes (e.g. it's a complete self-contained
    mini-app with its own Check/New-Problem controls, like MG6_BarModel),
    it isn't a "visual" skill — wire it as a "standalone" skill instead
    (StandaloneLevelSkill in levelSubsections.ts). ProblemRenderer mounts
    a standalone skill with zero injected props and no wrapper buttons;
    the component is trusted to be fully self-sufficient.

EXCEPTION — large packages with real internal module structure: the flat-
prefix rule above is for a handful of files (6-8) that only exist to
support ONE entry component. MM1_RatioLab is a different scale entirely:
27 files organized into genuinely reusable subdirectories (diagrams/,
engine/, lib/, units/) that cross-import each other, not just one
component's private helpers. Flattening + prefixing all 27 would make
every filename and every cross-import longer for no real benefit. For a
package at this scale:

  - The entry file (e.g. MM1_RatioLab.tsx) stays directly in the level
    folder, same as always — this is what keeps it visible to the admin
    file browser (LevelFilesPage's glob only goes one level deep, so
    anything nested inside a subfolder is automatically invisible there,
    the same outcome supporting-file filtering achieves for the flat
    case, just via folder depth instead of filename matching).
  - The package's internal subdirectories (diagrams/, engine/, lib/,
    units/ or whatever the artifact already called them) become real
    subfolders directly under the level folder, keeping their original
    short names and relative imports exactly as authored — don't rename
    or re-prefix files inside them.
  - If the artifact styles itself with a plain CSS file instead of
    Tailwind, check it for unscoped selectors (:root, body, html, bare
    button/input/h1-h3/p/img, etc.) before importing it anywhere. An
    artifact built to own its whole page will often reset these globally;
    imported as-is into a multi-page app, that silently repaints every
    OTHER page too. Rescope every selector under one wrapper class
    (MM1_RatioLab used .ratio-lab) — move :root's custom properties and
    body's visual properties onto the wrapper class itself, drop html-only
    rules, and rename any @keyframes to something collision-proof before
    they land in the site's global CSS namespace.
  - Vite's per-file esbuild transform (unlike tsc, which sees the whole
    program) needs type-only imports marked explicitly — `import { foo,
    type Bar }` or `import type { Bar }` — when importing an interface
    from another file in the package. Without it, the build still
    "succeeds" but prints a warning per occurrence that the import
    doesn't exist at runtime. tsc won't catch this; only an actual
    `vite build` (not just `tsc --noEmit`) surfaces it.

- Stacked ("handwritten") fractions everywhere, opt-in per lab (added
  2026-11 for MG10, user requirement: "I don't want to see 1/2"). Wrap the
  lab's content in <StackedFractions> (shared/components/MathText.tsx) and
  its own hand-written text (Explore, CFU, Key Idea, goals) in <MathText>.
  The shared engine already runs prompts, stories, hints, feedback,
  choices, answer chips, test review and captions through MathText, which
  turns "3/4", "2 3/4" and "?/12" in text into stacked fractions with a
  screen-reader name ("2 and 3 over 4"); outside the provider it changes
  nothing. In opt-in labs a dropdown whose options hold fractions becomes a
  TapSelect, scores read "8 out of 10", a typed top over a printed
  denominator uses SentenceStep.overDen (never "/12" text after a box), a
  CFU box that takes a fraction uses CfuBlank.mixedFraction, and SVG labels
  are drawn stacked by the lab's own helper (MG10 diagrams/SvgMath.tsx) —
  SVG <text> can't hold the HTML version. Promote SvgMath on its second
  consumer.
  Added with MG9 (2026-11): SvgMath is now shared
  (shared/components/SvgMath.tsx, plus SvgMathLine for a caption with
  fractions in running text). Inside the provider, the shared PieceBars
  unit labels, FractionBar label, TwoTierBars captions and NumberLine point
  labels draw stacked on their own. A typed top over a printed denominator
  in a NumberStep uses NumberStep.overDen (never suffix "/8"); a "type the
  top and the bottom" SentenceStep uses SentenceStep.stacked (never " / "
  between two boxes). MathText doesn't walk into components: text passed as
  children to QA/QB/Stepper etc. needs its own <MathText>, and a CFU
  dropdown followed by "/6" becomes <Frac n={box} d={6} />.
  Added with the all-labs pass (2026-11): every lab except MG9/MG10 is now
  opted in (score text reads "N out of 10" everywhere). Inside the provider
  QA/QB/QC, Says, Segmented labels, Slider labels and problem/test
  `visual`s also run through MathText. A typed fraction answer in a
  NumberStep uses NumberStep.fracBoxes ("fraction" = top over bottom,
  "mixed" = whole box + top over bottom; the boxes are joined back into
  "3/4" / "2 1/4" text, so grading is unchanged) — never "(Type it like
  1/3)". A RatioStep whose two boxes are one fraction uses
  RatioStep.stacked. Don't put a letter right after a fraction ("1/3s")
  or it won't stack; write "copies of 1/3".

- "Pick the kind of answer" for fraction answers, opt-in per lab (added
  2026-11 for MG10, user request: students didn't know to leave the
  whole-number box empty for 3/4). Wrap the lab's content in
  <AnswerFormPick> (shared/components/AnswerForm.tsx; logic in
  answerKinds.ts). Every FractionStep with `mixed: true` and no printed
  `den`, and every CfuBlank.mixedFraction, then starts with three tap
  buttons: Whole number · Mixed number · Proper fraction. Nothing is picked
  at the start (a default gives the kind away); the boxes appear once a kind
  is picked, Check stays disabled until every shown box is filled, and
  switching kinds keeps the numbers that still fit. Grading says whether the
  kind was right (button green/red; "Mixed number is right. Check the
  numbers."; a wrong kind's 2nd try names the right kind), and ANY wrong
  Check on such a step makes the solve not clean (StepState.formMiss). The
  Test shows the buttons with no feedback, and the review list adds the
  picked kind: "5/4 (proper fraction)". Teach the kinds once with
  <AnswerFormGuide /> in Explore. Steps with a printed `den` ("?/12") and
  labs without the provider are unchanged. Round 5 (user): every set of
  buttons has the line "Pick a format to write your answer." just above it
  (FormPicker's `prompt`, FORM_PICK_PROMPT; the user's word "format", keep
  it), in Practice, CFUs and Tests. A step's `diagnose` message (e.g. "You
  added across…") is shown even when the picked kind is also wrong, ahead of
  the kind message, then one plain line: "The correct answer is not a …".
  Feedback and screen-reader names say "format" too, never "kind of answer".

- FractionStep.diagnose(num, den, typed?) gets the answer exactly as typed
  ("2/2", "1 3/5"), so a named mistake quotes the student's own number
  instead of a reduced one. Optional; diagnoses that ignore it are unchanged.

- A "fill in the reason" sentence frame (MG10 round 6, the add-across judge
  step) is a SentenceStep with three optional fields: `more` (blanks 3+,
  each followed by its own text), `checkEach` (every select blank is tap
  buttons, Check stays off until every blank is filled, a wrong Check colors
  each pick green/red, a wrong Check counts against a clean solve, and the
  row wraps like text via .sentence-frame), and `diagnose(inputs)` (a short
  message for the first wrong blank). Use it when a fact always comes out
  the same way: the student states the reason with this problem's numbers
  instead of tapping one fixed button. Steps without these fields are
  unchanged.
